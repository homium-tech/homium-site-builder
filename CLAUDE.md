# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Package manager is **pnpm** (not npm — the system prompt sent to the AI engines explicitly mandates `pnpm`).

```bash
pnpm start              # Run the Express server (node server.js) — http://localhost:8080 (or $PORT)
pnpm run dev             # Same as start, no watch mode
pnpm run setup           # Interactive install/diagnostic wizard (scripts/setup.cjs)
pnpm run doctor          # Same wizard, check-only (no installs) — scripts/setup.cjs --check-only
pnpm run install:playwright  # Optional: installs Chromium for forensic URL extraction
pnpm test                # Runs every test file under test/ sequentially (see below)
```

There is no test framework — each file under `test/` is a standalone Node script using `assert` with a hand-rolled runner, and prints its own pass summary. Run one file directly to isolate it:

```bash
node test/agent-engine.test.js
node test/deliverable-store.test.js
node test/multi-engine.test.js
node test/workspace.test.js
node test/pipeline.test.js
node test/cli-spawn.test.js           # CLI executable resolution without a shell
node test/message-heuristics.test.js  # question/request/brand-name classification
node test/off-topic-flow.test.js      # deviation rule, pending step, lastAction
node test/format-text.test.js         # formatText sanitization (extracted from public/app.js)
node test/persistence.test.js         # chat/state persistence across reloads
node test/engine-reliability.test.js  # stream parsing, single done/error, failed/cancelled turns, timeout, HTTP adapters
node test/history-durability.test.js  # atomic chat_history.json, corrupt-file quarantine, 500-message cap, session eviction
node test/server-chat.test.js         # boots the real server with the mock engine: /api/chat, 409, disconnect, cancel, reset
node test/server-security.test.js     # real server: Referer isolation of previews, CORS/403, login limiter, TRUST_PROXY
node test/server-gates.test.js        # real server: gate detection, approved/adjusting status, F5 inference, /api/project/new
node test/client-render.test.js       # runs public/app.js in a vm with a fake DOM: escaping of state-derived HTML, Blueprint inference
node test/prompt-contract.test.js     # prompt invariants, APP_ROOT paths, state digest, pending-step ordering
node test/scripts.test.js             # compile/audit/verify_fidelity run by absolute path; template/audit/docs stay in sync
```

Tests that touch disk use a `scratch_test_*` dir under `test/` and clean it up themselves.

No lint/typecheck script is configured.

## Required environment (.env)

The server refuses to authenticate without `AUTH_PASS`. Copy `.env.example` → `.env`:

- `AUTH_USER`, `AUTH_PASS` — login credentials (compared with `crypto.timingSafeEqual`)
- `SESSION_SECRET` — session signing secret (random if unset, meaning sessions reset every restart)
- `PORT` (default `8080` — same as the default llama.cpp port, so set one of `PORT` / `LLAMACPP_HOST` if you run both; `README.md` still says `3000`, which is stale), `HOST` (default `0.0.0.0`)
- `ALLOWED_ORIGINS` — comma-separated extra origins allowed through CORS/`requireSameOrigin` (e.g. `http://apps.homium.tech:8080`). Required if the app is exposed under any domain other than `localhost`/`127.0.0.1`/`::1` — otherwise every `/api/*` call (chat, tabs, SSE) is silently blocked while `/login` still loads fine
- `WORKSPACE_DIR` / `WORKSPACE_ROOT_DIR` — where generated projects live (default `~/Downloads/homium_projects`, **outside the repo**)
- `LLAMACPP_HOST`, `OLLAMA_HOST`, `OLLAMA_MODEL` — for the local server-based engines

## Architecture

This is a chat-driven, multi-engine AI orchestrator that drives a **fixed 5-phase design pipeline** (Discovery → Foundations → Components → Validation → Prototype) to autonomously produce a Homium-branded design system and a 3-page vanilla HTML/CSS/JS prototype. The Express server (`server.js`) is mostly plumbing; the actual "intelligence" is a system prompt sent to whichever CLI/API engine is selected, and the server's job is to supervise disk output and relay the conversation.

### Request flow

`server.js` → `AgentEngine.executeTurn()` (`lib/agent-engine/index.js`) → engine-specific **adapter** (`lib/agent-engine/adapters/*.js`) spawns a child process or makes an HTTP call → stdout is parsed by `StreamParser` into `text_delta`/`tool_activity`/`log` chunks → wrapped in a `TurnStream` (EventEmitter + async-iterable) → `TurnStream.pipeToSSE()` streams `chunk`/`metrics`/`done`/`error` SSE events straight to the browser at `POST /api/chat`.

- **Adapters** (`lib/agent-engine/adapters/`) implement the `EngineAdapter` seam (`buildCommandAndArgs`, `spawnTurn`) for 7 engines: `claude`, `agy` (Antigravity), `codex`, `opencode`, `llamacpp`, `ollama`, `mock`. The mock adapter simulates responses in-memory for testing with no external calls. `agy` can lose its model stream mid-turn: it emits an `error_message` step, retries the generation from scratch (the text restarts) and may end with exit code 0 but `result.status: "ERROR"`. `AgyEventTracker` (in `agy-adapter.js`) drops the aborted attempt by emitting a `reset` chunk (`keep` = chars of the reply to keep; applied by `AgentEngine`, `pipeToSSE` and `public/app.js`) and fails the turn when no complete answer remains, so a cut reply is never saved as a finished turn. Adding a new engine means adding one adapter file and registering it in `AgentEngine`'s constructor.
- **Prompt construction** (`AgentEngine.executeTurn`) is stateful per-session per-engine: the *first successful* turn for a given engine injects the full canonical activation prompt (`core/prompts/system-rules.js` → `buildActivationPrompt`, workspace-scoped; a failed first turn is not counted, so the retry re-sends it). *Subsequent* turns inject a compact directive that **repeats every turn** the rules single-turn engines cannot remember (`FORMAT_INVARIANTS`, `REVISION_RULE`, `STATE_CONTRACT`, `STAGE_MAP`, the `DEVIATION_RULE`), a tooling note with the absolute `APP_ROOT`, a **bounded digest** of `design-system-state.json` (`buildStateDigest`, never the whole file — an invalid JSON is reported to the agent instead of skipped), the clipped last exchange and, last, the pending step. The agent runs inside the project folder, so scripts/templates/references are always referenced by absolute `APP_ROOT` paths (`{{APP_ROOT}}` in the directives and `<APP_ROOT>` in `references/phases/*.md`).
- **`core/prompts/system-rules.js`** is the actual canonical spec the AI must follow: the golden rule (Directiva 0: ask instead of assuming; inferences are hypotheses), single-question-rule, strict phase ordering (the Brand Equalizer is Stage 1.6, closing Phase 1 and resolved before palette/typography, as in `Prompt - Design System.docx`; there is no Stage 2.3, and 2.4–2.6 keep their numbers), mandatory numbered options with a "custom" option always last, WCAG 2.2 AAA color constraints, "no emojis in UI," "no brackets in labels," pnpm-only, and the hard rule that the pipeline **must terminate at Phase 5** (never invent a Phase 6 / scaffolding / frameworks). Treat this file as the product spec, not incidental config.
- **`core/pipeline/index.js`** (`Pipeline` class) is the *server-side*, source-of-truth mirror of that same 5-phase structure (`CANONICAL_PHASES`) plus `detectAction()`, which returns a sanitized (non-regex) descriptor **only for the two approval gates** (`gate-1` Design System, `gate-2` Prototype). Detection looks at the last question of the current step (text after the last `---`, with the Blueprint `>` block and summary tables removed, accents/markdown normalized), requires an approval verb and classifies it; a closed gate ("Compuerta 1 aprobada…") or a phase confirmation never opens one. The Phase 3 closing question in `references/phases/phase-3-components.md` is worded "¿Apruebas el catálogo para avanzar a la Fase 4 … showcase?", so a question that moves forward to Fase 4 / Validación Visual (without Fase 5 / prototipo) is never a gate. As a second layer, `server.js` `gateHasDeliverable()` (via `Pipeline.isGateReady`) drops any gate whose deliverable is missing on disk (gate-1 needs the `*_Design_System.html` showcase, gate-2 needs `prototype/index.html`), both when a reply is saved and when a stored `lastAction` is replayed by `/api/chat/history`. Numbered options of interview questions are not described by the server: the agent writes them in its reply. `matchGateResponse()` recognizes the gate buttons (or a typed "Aprobado") so the server can record the gate status. `PhaseRegistry`/`PhaseDescriptors` are backward-compat aliases around the same class. There is no advanced/expanded phase set anymore (`ADVANCED_EXPANSION_PHASES` is empty and `enableAdvancedPhases()` is now a no-op that always re-pins to the 5 canonical phases) — don't build features assuming otherwise.
- **`lib/workspace/index.js`** (`Workspace`) owns the on-disk sandbox: resolves the base dir (`WORKSPACE_DIR`/`WORKSPACE_ROOT_DIR` or `~/Downloads/homium_projects`), derives a per-project subfolder slug from the user's first message (`extractProjectName`, Spanish-language heuristics + URL parsing), persists the active project via a `.active_project` marker file, and emits `projectChanged` so `server.js` can re-point `AgentEngine` and `DeliverableStore` at the new directory live. All generated deliverables must stay confined under this dir — never in repo-relative paths or hidden CLI config dirs.
- **`lib/audits/index.js`** (`runGateAudits(gateId, dir)`): when a gate opens, `server.js` (`withGateAudit`) runs the mechanical audit scripts itself on the files on disk (gate-1: `audit_showcase` + `audit_spec` + `verify_fidelity --check A` on the showcase; gate-2: `verify_fidelity` + `audit_prototype` on `prototype/`) with `spawnSync`, no shell, 15 s timeout, and attaches `{ checks, summary, ranAt }` to the gate action as `action.audit`, both on the reply (`transformDone`) and when `/api/chat/history` replays it after a reload (recomputed, never trusted from the stored copy). The client renders it in `renderGateAudit` inside the gate card. It is **informational only**: errors never disable the Approve button, and an audit that fails to run never hides the gate. The point is that the user sees the real result instead of the agent's own summary of it.
- **Fidelity limitations report (gate 2)**: `runGateAudits('gate-2')` also attaches `action.audit.fidelity` (`{ mode, items, coverage, verify }`) from `scripts/fidelity_report.cjs`, a static, always-exit-0 script. It lists what the prototype does not replicate from the reference and why, as items `{ kind, title, reason, instead? }` with `kind` = `sustituido` (font not loaded by the prototype → fallback, third-party video), `no_replicado` (smooth scroll, custom cursor, canvas/WebGL), `parcial`, `no_capturado` (extraction coverage, missing visual comparison) or `nota_agente`. Fonts are checked in every mode; motion, hero, coverage, secondary pages and the visual comparison only in `TOTAL_ARCHITECTURAL_FIDELITY`. The agent adds what the disk cannot show in `state.fidelity_notes` (`[{ topic, reason, substitute }]`, part of `STATE_CONTRACT`). `verify_fidelity --visual` writes `scratch/fidelity_verify.json` (hero/full-page/section similarity + timestamp; the report marks it stale if the prototype changed later) and now also scores `full_page` (warning < 0.80, critical < 0.65 in strict mode). The client renders it in `renderFidelityReport` inside the gate card; like the audits it is informational and never blocks Approve.
- **Extraction coverage**: `extract_reference_dna.cjs` measures `structural_blueprint.global.coverage_pct` (captured height ÷ `<main>`/document height, plus `captured_height_px`, `coverage_base_px`, `coverage_before_pct`); below 70 % it adds the sibling blocks of the chosen sections (`pickBlocks`). It also captures `navbar.menu_overlay` (links of a closed overlay menu + trigger button) when `nav_links` only holds skip links, `hero.heading_color_runs`, `hero.page_canvas_count`, `left_px`/`top_px`/`position` per media slot and cookie notices without "cookie" in their id/class (fixed elements whose text mentions cookies/analytics/privacy). The extractor refuses loopback/private hosts, so test it against a scratch copy with those guards removed, never by weakening the real ones.
- **Header and footer fidelity**: they give a page its personality, so they are copied 1:1 and compared with `critical` severity. The extractor finds the header by geometry when the site has no `<nav>`/`<header>` (Framer, Webflow: a fixed/sticky/absolute block near the top with the most interactive children, then refined to the smallest styled element that holds them, i.e. the pill) and records `navbar.detected_by`, `brand`, `link_items` (every clickable text, `div`/`span` included), `icon_links`, `shadow`, `width_px`/`left_px`/`top_px`. The footer is looked up with a rendered-not-in-viewport test (the old `qsVisible` never found a footer below the fold) and, without `<footer>`, as the outermost block that ends at the bottom of the document (`footer.detected_by`). When nothing could be read the blueprint says so (`navbar.capture_failed`, `footer.capture_failed` / `reason: no_footer_found`) and `ref_header.webp` / `ref_footer.webp` are the visual anchor. `verify_fidelity` `checkNavbar` compares shape, width/offset, shadow, background, link count (invented links are critical), icon controls and brand; `checkFooter` compares links (±1 warn, ≥2 critical), social, newsletter, ©, height and background. An empty blueprint is a `WARN` plus a band comparison against the reference screenshot, never a silent `PASS`. `fidelity_verify.json` is rewritten on every run (keeping the last `--visual` measurement) with the header/footer issues, and the report lists sections < 80 %, coverage 70-90 %, and header/footer differences. `FIDELITY_RULE` (system prompt, short form every turn) forbids inventing header/footer links and forbids claiming "validated/approved" in the gate message: the card shows the real audits.
- **Turn log (`lib/turn-log/index.js`)**: `AgentEngine` takes a `turnLogger` and calls it exactly once per turn (`done` / `error` / `cancelled`) with `{ at, sessionId, engine, outcome, durationMs, promptChars, responseChars, resets, error }` — never the conversation content. `server.js` appends it to `<project>/turns.jsonl` (halved when it passes 1 MB; unreadable lines are skipped) and exposes it at `GET /api/turns?limit=`. The `done` SSE event also carries `engine` and `resets`, and the Consola tab prints duration and agy retries.
- **Interrupted turns**: when no turn is running, `GET /api/chat/history` calls `Workspace.dropUnansweredUserMessages()` — trailing user messages with no reply (a turn the server never closed, e.g. a restart) are removed from `chat_history.json` and returned as `interrupted`; the client logs a notice and puts the last one back in the input box. Without this the orphan blocked the numbered options of the last question.
- **Finished-project card**: `renderProjectFinished` (client) shows download / view-prototype actions in the gate container when `state.status === 'PROYECTO_FINALIZADO'`; it never overwrites an open gate and is repainted after `evaluateInteractiveActions` clears the container.
- **`lib/deliverable-store/index.js`** (`DeliverableStore`) watches the workspace directory on disk (debounced) and exposes an O(1) in-memory snapshot plus an SSE channel (`GET /api/deliverables/stream`) so the frontend reacts to file changes (state JSON, showcase HTML, prototype files) with zero polling.

- **Live preview follow**: the snapshot's `status` carries `showcaseVersion` / `prototypeVersion` (mtime+size signatures), so `DeliverableStore` emits `change` when an existing HTML is rewritten, and the client reloads the matching iframe (`?v=` cache-buster). `app.js` `followLiveTab()` switches tabs by `current_phase` (1-3 Blueprint, 4 Showcase, 5 Prototype; deliverables that already exist can only move it forward); a manual tab click pauses it until the target changes. The "En vivo / Pausado" pill (`#followIndicator`) is a read-only indicator (`pointer-events: none`, not a button) so a stray click never steals an adjacent tab click; there is no manual on/off switch anymore. `renderBlueprint()` wraps `renderBlueprintRaw()` to flash whatever changed between renders.
- **Off-topic / deviation handling**: nothing server-side blocks a message; the agent is steered by prompt. `DEVIATION_RULE` (directive 17, also in the compact per-turn directive together with `STAGE_MAP`) tells the agent to answer briefly or refuse, then `---` and repeat the pending question; its exception is `REVISION_RULE` (directive 18): asking to change a confirmed decision, go back to a stage, redo a phase or start another project is *not* a deviation. The pending question survives because `AgentEngine` keeps `session.pendingStep` (last agent reply whose **heading** is an `Etapa N`/`Fase N` with N in 1-5 — `isFlowMessage` is anchored to line start, so prose like "estamos en la Fase 2" or "no puedo abrir una Fase 6" does not count) and the server also passes `workspace.getPendingStep()` from `chat_history.json`, so it is re-injected even after the deviation reply itself. Claude engine turns are stateless (`claude -p`, no `--session-id`), so this block is the only memory of the position. `core/text/message-heuristics.js` is a UMD module shared by Node (`Workspace.extractProjectName`, `Pipeline.detectAction`) and the browser (served at `/message-heuristics.js`, used by `inspectUserMessageForState`): questions/requests/greetings/commands never become a project or brand name, a URL inside a sentence is a design reference (only a message that *is* a URL names the project), and when the user message is a request `detectAction` only looks at the part after the last `---` and only if it is a flow step. `lastAction` in the history is kept through deviations and cleared when the flow advances to a step without controls; the client restores the pending gate after a deviation.
- **Spawning CLI engines**: adapters never use `shell: true`. `lib/agent-engine/adapters/cli-spawn.js` resolves the real executable (env override `CLAUDE_BIN`/`AGY_BIN`/`CODEX_BIN`/`OPENCODE_BIN`, known paths, then PATH; npm `.cmd` shims are unwrapped to the `.exe`/JS they launch) so the prompt reaches the child intact. On Windows, `shell: true` splits the prompt on spaces and cmd.exe interprets `& | > %` in it. If you add an adapter, use `resolveInvocation` too.
- **`formatText` (public/app.js)** renders agent output as HTML: text is escaped including quotes, links are limited to `http(s)` or site-absolute paths, file-link paths are re-escaped after `decodeURIComponent`. The chat chip/card tray (`#dynamicActionTray`) is deliberately hidden by CSS (`display: none !important`, commit b761803); the visible interactive control is the approval gate.
- **Reload/persistence**: `GET /api/chat/history` rebuilds the UI after F5 from `workspace.getChatHistory()` (messages + last pending action + `gates`) plus `deliverableStore` state, and reports `busy` while a turn is still running. `chat_history.json` also stores the status of each gate (`approved` / `adjusting`, set when the user answers the gate, cleared when the agent reopens it, restored if that turn fails); the fallback that infers a gate from the deliverables on disk only fires for gates not yet resolved. History writes are atomic (tmp + rename), capped at 500 messages, and a corrupt file is moved to `chat_history.corrupt-<ts>.json` instead of overwritten. The client also keeps `homium_site_builder_session_id`, the preferred engine, and a cached resumed-project payload in `localStorage`. `POST /api/reset` cancels running turns and archives state + history; `POST /api/project/new` leaves the current project untouched on disk so a later message with the same brand name resumes it.

### Frontend

Single-page app served from `public/`: `index.html` + `app.js` (client SSE consumption, chat UI, telemetry panel) + `styles.css`. `public/homium/` holds the packaged Homium Design System tokens/fonts/logos used both by the app UI and by every generated deliverable preview. `login.html` is a separate unauthenticated route.

Preview routes (`server.js`) render generated deliverables directly from the workspace with a standardized "waiting" placeholder page when a phase hasn't produced its artifact yet:
- `/preview/prototype` — Phase 5 output (`prototype/index.html`)
- `/preview/showcase` — Phase 4 output (`*_Design_System.html` in the workspace root)
- `/preview/blueprint` — Phase 1 architectural blueprint, driven by `deliverableStore` state

### Security posture (already implemented, follow the same patterns)

Session-cookie auth (`express-session`, `httpOnly`, `sameSite: strict`) gates everything except `/login` and `/api/auth/login`. Login uses `crypto.timingSafeEqual` for constant-time comparison and a per-IP rate limiter (10 attempts / 15 min). CORS and a `requireSameOrigin` middleware restrict `/api/*` to same-origin/localhost. `/preview/*` gets its own CSP with a sandboxed iframe policy since it renders AI-generated HTML.

### Reference/knowledge base (not code, but shapes what the engines generate)

- `references/phases/phase-{1..5}-*.md` — detailed per-phase specs mirroring `core/prompts/system-rules.js`
- `references/component-catalog.md`, `token-architecture.md`, `brand-equalizer.md`, `accessibility-checklist.md`, `interactive-states.md` — design-system knowledge base the AI draws on
- `templates/design-system.html` / `.md` — the mandatory structural base for the Phase 4 showcase (must keep all **14** canonical sections + Left Rail Sidebar — the sitemap phase was removed, so there is no `sec-sitemap`; `scripts/audit_showcase.cjs`, the template and `phase-4-validation.md` are kept in sync by `test/scripts.test.js`; the system prompt explicitly forbids generating a simplified showcase from scratch)
- `scripts/audit_spec.cjs` — audits the Phase 4 master spec (`[Brand]_Design_System.md`) the way `audit_showcase.cjs` audits the HTML: fails on any `{{placeholder}}` (also inside code blocks), leftover template `<!-- -->` comments (outside code blocks), a missing `## SECCIÓN 1..5`, or an export format chosen in stage 4.1 (`export_format` in the state) with no block in SECCIÓN 5; warns on `(Opcional)` headings left on generated sections and on hexes outside `palette.allowed_hexes`. Invoked by `references/phases/phase-4-validation.md` by absolute `APP_ROOT` path; `test/scripts.test.js` keeps it in sync with `templates/design-system.md`.
- `templates/prototype/` (`base.html`, `base.css`, `base.js`) — accessibility/behavior base for the Phase 5 prototype, **not a visual template** (the layout still comes from the blueprint): skip link, `aria-current`, drawer closed with `visibility: hidden` + `inert`, menu button with `aria-expanded`, focus management and Escape, theme toggle, count-up and a canvas loop that respect `prefers-reduced-motion` and pause off-screen. `test/scripts.test.js` asserts that the base, once its `{{MARKERS}}` are filled, passes `audit_prototype.cjs` at 100%. The delivery rules (approved fonts only, the chosen icon system as inline SVG, focus ring ≥ 3:1 per theme, per-theme accent/status tokens, no inline styles, sample content for data the user did not give) live in the "Reglas de Entrega del Prototipo" block of `references/phases/phase-5-prototype.md`. Note the guide still allows CDN libraries (Three.js, GSAP, Lenis…) when the reference blueprint calls for them; `audit_prototype` only warns about them.
- **Chat Blueprint folding**: every agent reply starts with the cumulative Blueprint quote (Directive 15). `public/app.js` `splitBlueprintBlock`/`renderChatBlueprint` render it as a collapsed `<details class="chat-blueprint">` (already visible in the Blueprint tab); `renderAgentMessage` wraps `renderAgentBody` and is used while streaming, on completion and when history is replayed.
- `scripts/audit_prototype.cjs` — static (no browser) audit of `prototype/` that mechanizes the Phase 5 "Checklist Manual Complementario": per theme (`:root` plus every `[data-theme="x"]`) it resolves the CSS variables and measures text colors against their own or the page background (< 3:1 fails, < 4.5:1 warns) and the `:focus`/`:focus-visible` ring **composited with its alpha** (< 3:1 fails); fails on an off-canvas drawer with no `visibility: hidden`/`inert`, a menu button without `aria-expanded`, and missing `lang`/`<title>`/viewport/`<main>`/`<h1>`, `alt` or form labels; warns on link/button rules whose optimistic estimated height (height/min-height, else font-size × line-height, plus vertical padding when the rule sets a block-ish display) is under 24px (WCAG 2.5.8), missing focus styles, skip link, `aria-current`, external dependencies, fonts outside `state.typography`, an unused icon system, many inline styles and a never-paused `requestAnimationFrame`. It strips `@import` before splitting CSS rules (Google Fonts URLs contain `;`). Invoked by `references/phases/phase-5-prototype.md`; covered by `test/scripts.test.js`.
- `scripts/contrast.cjs` — pure WCAG helpers (`parseColor`, `contrastRatio`, `pickReadable`) shared by `compile_showcase.cjs` and `audit_showcase.cjs`. `audit_showcase.cjs` fails on real contrast errors of the showcase chrome (text vs the background it is painted on, including the left rail over `--bg-sunken`, text on accent and `--client-*` semantic colors) and warns below AAA. The template gives the rail its own `--rail-*` tokens and `--fg-muted`/`--fg-subtle` at 0.82/0.68.
- `scripts/compile_showcase.cjs`, `scripts/verify_fidelity.cjs`, `scripts/extract_reference_dna.cjs`, `scripts/audit_showcase.cjs` — CJS scripts the AI engines are instructed to invoke (phases 1/4/5) **by absolute path under `APP_ROOT`** from inside the project folder, not app code invoked by the server itself. `verify_fidelity.cjs --check A --file <html>` runs only the chromatic allowlist on one file (used on the Phase 4 showcase). `compile_showcase.cjs` needs an explicit state path and is not invoked by the prompt: it reads `modular_scale` / `density_mode` from the state and computes the WCAG table from the real colors, but part of its sample content is still fixed, so agents build the showcase on the template instead.

### Language and repo quirks
